# Interaction History Design

## Goal
Provide fine-grained visibility into every interaction within a workbook element by storing timestamped snapshots of exercise state, scaffolding hints, and grading outcomes. The Interaction History should enable instructors to audit learner progress, help desks to debug issues, and analytics services to derive insights.

## Scope
- Track all state transitions for interactive exercises (inputs, intermediate calculations, submissions).
- Record scaffolding hints generated by the tutoring system along with their delivery context.
- Capture grading attempts, their results, and feedback payloads.
- Associate each record with the corresponding workbook element, user, session, and timestamps.
- Expose read APIs for instructors, analysts, and debugging tools.

## User Stories
1. **Instructor review**: An instructor can inspect a learner's full activity timeline to understand misconceptions.
2. **Support debugging**: Support staff can replay an interaction to reproduce a reported bug.
3. **Analytics pipeline**: Data engineers can export interaction histories to train adaptive learning models.

## Functional Requirements
- Persist ordered interaction events per workbook element instance.
- Support filtering by user, timeframe, exercise, and event type.
- Provide pagination/streaming for long histories.
- Allow event payload schemas to evolve without migration downtime (e.g., via versioned payloads or schemaless storage).
- Integrate with existing grading/scaffolding services to capture emitted events.

## Non-Functional Requirements
- Low write latency to avoid slowing live interactions.
- Durable storage with retention policies (e.g., configurable per course).
- GDPR/FERPA compliance: PII encryption at rest, deletion workflows, consent tracking.
- Access control: role-based permissions on viewing histories.

## Architecture Overview
```
Client UI --> Interaction SDK --> Event Bus --> History Service --> Storage (append-only log)
                                      |                               |
                                      |--> Notification hooks ---------
```
- **Interaction SDK**: emits structured events (state snapshot, hint delivered, grade result) with metadata.
- **Event Bus**: Kafka/PubSub channel decoupling producers from consumers.
- **History Service**: validates, enriches (e.g., resolves user/course IDs), persists to storage, and exposes querying API.
- **Storage**: append-only log (e.g., DynamoDB Streams, PostgreSQL table with partitioning, or cloud log service) optimized for chronological queries.
- **Notification hooks**: optional webhooks for real-time monitoring or analytics ingestion.

## Data Model
- **Event**
  - `event_id` (UUID)
  - `element_instance_id`
  - `user_id`
  - `session_id`
  - `course_id` / `workbook_id`
  - `timestamp`
  - `event_type` (`STATE_SNAPSHOT`, `HINT`, `GRADE_RESULT`, ...)
  - `payload_version`
  - `payload` (JSON/BSON blob capturing state diff, hint text, grading rubric, score, etc.)

## API Sketch
- `POST /interaction-history/events` (internal)
- `GET /interaction-history?elementInstanceId=&userId=&from=&to=&eventType=`
- SSE/WebSocket stream for live monitoring (optional).
- Bulk export job configuration for analytics.

## Integration Points
- **Grading pipeline**: emit grade attempts/results.
- **Scaffolder service**: emit hint generation/delivery events.
- **Exercise runtime**: capture UI state before/after key actions (submission, hint request, auto-save).

## Privacy & Compliance Considerations
- Allow per-course redaction policies.
- Support anonymized exports for research.
- Audit trail for access.

## Open Questions
- Do we store full state snapshots or diffs? (trade-off storage vs. replay fidelity)
- Required retention period per institution?
- Need for real-time dashboards vs. batch exports?
- Should learners have access to their own interaction history UI?

## Rollout Plan
1. Define event schema & SDK instrumentation guidelines.
2. Implement backend ingestion service and storage adapters.
3. Pilot with limited set of exercises and instructors.
4. Add UI tooling for instructors/support.
5. Iterate on performance and retention policies.
