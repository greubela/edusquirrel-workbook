# Worker execution backend

`client.js` owns the GUI. `worker.js` starts `WebWorkerBackendServer` in a dedicated
browser worker, installs a message listener, and executes commands through
`WorkerCommandHandler`. Its `Future`s run on the worker's event loop, so CPU work
cannot block the GUI event loop. The worker itself still processes synchronous
CPU work sequentially; multiple workers are needed for multiple CPU jobs at once.

The shared `WorkerExecutionProtocol` wraps `ExecutionCommand` and
`ExecutionClientResponse` with a `requestId`. Responses retain typed serialized
results, errors, timestamps and logging output. `WebWorkerExecutionClient`
implements `ExecutionClient`, including `handleCommand`, `executeResponse`,
`ExecutionCommandFactory.sendCommandTo`, and pooling. It correlates simultaneous
requests, ignores duplicate/late IDs, and validates returned command identity.
Crashes, undecodable messages, posting failures, timeouts and `close()` fail
pending requests. Timeouts terminate a stalled worker; execution never silently
falls back to the GUI thread. Obtain a new client after termination.

`fullInfo.defaults.workerBackendExecutor` is a shared lazy client. Scala.js
`OptionalRuntimeStartup` warms that same client after the overview paints, or a
command starts it on demand. The JavaScript bootstrap starts no workers.
`EDUSQUIRREL_BACKEND_MODULE_WORKERS=0` disables background backend warmup;
positive values warm the one shared execution client. An optional
`EDUSQUIRREL_BACKEND_MODULE_WORKER_SCRIPT` configures its URL before creation.
The HTTP backend remains available as `backendExecutor`; server-only commands
are not advertised by the worker. Both bundles are generated by `sbt buildJS`.
The legacy `backend-worker.js` Pages alias remains available for old links.

Editor Python execution uses `PythonCommandWorkerPreheat`, which warms one
isolated command worker with an empty Python request after first paint. The
first editor takes ownership of that worker, so Run avoids interpreter startup
and Stop/close can terminate it without disrupting the shared backend client.
Later independent execution sessions receive separate workers. Failed unused
warmups are closed and may be retried; optional downloads never gate the overview.


See [execution clients](execution-clients.md) for local/HTTP selection and a complete
typed command definition. Use an existing worker factory from a client scope with `fullInfo`, XML and an
implicit execution context, for example:

```scala
WorkerCommands.parseSnapXml.sendCommandTo(
  fullInfo.defaults.workerBackendExecutor,
  WorkerCommands.ParseSnapXmlRequest(xml, "block")
).map(_.result)
```

Supported commands are `worker.health`, `worker.parseSnapXml`,
`worker.calculateQrCode` and `worker.runPython`. XML parsing uses the existing dependency-free Snap
parser and its documented Snap XML subset, not a general XML parser. QR execution
returns resolved metadata and the full module matrix after mask selection.
Python runs lazily load Pyodide 0.29.3 inside the worker. Requests use JSON values
for context and return a JSON-compatible final expression, stdout, stderr and
recorded callback operations. Callback modules declare method names, not live
JavaScript functions. Explicit packages and packages discovered from imports are
loaded before execution. Python jobs queue within each worker, so asynchronous
runs cannot mix their globals, callbacks or captured output. Other command types
can still execute while Python awaits loading or asynchronous operations.

```scala
WorkerCommands.runPython.sendCommandTo(
  fullInfo.defaults.workerBackendExecutor,
  WorkerCommands.RunPythonRequest("print('Hello')\n6 * 7")
).map(_.result) // value = 42, stdout = "Hello\n"
```

`resetGlobals` defaults to true and creates a fresh execution namespace without
reloading the interpreter. False retains variables between jobs in the same
worker. Imported modules remain interpreter state; this is not a sandbox or a
fresh Python process. Python errors use the command failure envelope, with
captured output retained in its logging fields. A subsequent job can still run.
Closing the client or its request timeout terminates the worker, including an
infinite Python loop. Use separate clients/workers to run Python jobs in parallel.

The editor's `PyodideTurtleCommandRunner` now uses this command protocol in a
dedicated worker, warms the interpreter during its startup deadline, and replays
the returned turtle callbacks. The legacy Pyodide worker APIs remain available
for their existing callers. DOM-dependent tasks stay on the client.
To add a job, declare its typed factory in `WorkerCommands`, register its handler
in `WorkerCommandHandler`, and include its name in `supportedCommands`.

Tests cover request correlation, failure cleanup, timeout behavior, unsupported
commands, typed result decoding, worker dispatch, and actual browser workers.
`tools/dev/worker-execution.browser.test.mjs` checks the built worker and verifies
that the GUI event loop keeps running during a version-40 QR calculation and
real Pyodide execution. The browser fixture serves the pinned Pyodide npm package
locally, so these checks need no external CDN access.
