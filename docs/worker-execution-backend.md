# Worker execution backend

`client.js` owns the GUI. `worker.js` starts `WebWorkerBackendServer` in a dedicated
browser worker, installs a message listener, and executes commands through
`WorkerCommandHandler`. Its `Future`s run on the worker's event loop, so CPU work
cannot block the GUI event loop. The worker itself still processes synchronous
CPU work sequentially; multiple workers are needed for multiple CPU jobs at once.

The shared `WorkerExecutionProtocol` wraps `ExecutionCommand` and
`ExecutionClientResponse` with a `requestId`. Responses retain typed serialized
results, errors, timestamps and logging output. `WebWorkerExecutionClient`
implements `ExecutionClient`, including `handleCommand`, `executeResponse`,
`ExecutionCommandFactory.sendCommandTo`, and pooling. It correlates simultaneous
requests, ignores duplicate/late IDs, and validates returned command identity.
Crashes, undecodable messages, posting failures, timeouts and `close()` fail
pending requests. Timeouts terminate a stalled worker; execution never silently
falls back to the GUI thread. Obtain a new client after termination.

`fullInfo.defaults.workerBackendExecutor` reuses a worker preheated by
`homepage/js/app-loader.js`, or starts `artifacts/newest/worker.js` on first use.
The HTTP backend remains available as `backendExecutor`; server-only commands
are not advertised by the worker. Both bundles are generated by `sbt buildJS`.
The legacy `backend-worker.js` Pages alias remains available for old links.

See [execution clients](execution-clients.md) for local/HTTP selection and a complete
typed command definition. Use an existing worker factory from a client scope with `fullInfo`, XML and an
implicit execution context, for example:

```scala
WorkerCommands.parseSnapXml.sendCommandTo(
  fullInfo.defaults.workerBackendExecutor,
  WorkerCommands.ParseSnapXmlRequest(xml, "block")
).map(_.result)
```

Supported commands are `worker.health`, `worker.parseSnapXml` and
`worker.calculateQrCode`. XML parsing uses the existing dependency-free Snap
parser and its documented Snap XML subset, not a general XML parser. QR execution
returns resolved metadata and the full module matrix after mask selection.
Existing Pyodide workers keep their separate initialization/protocol; this change
does not move Python runtimes or DOM-dependent tasks into the generic backend.
To add a job, declare its typed factory in `WorkerCommands`, register its handler
in `WorkerCommandHandler`, and include its name in `supportedCommands`.

Tests cover request correlation, failure cleanup, timeout behavior, unsupported
commands, typed result decoding, worker dispatch, and actual browser workers.
`tools/dev/worker-execution.browser.test.mjs` checks the built worker and verifies
that the GUI event loop keeps running during a version-40 QR calculation.
